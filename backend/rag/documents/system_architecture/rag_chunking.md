# RAG Document Chunking (Splitting the Knowledge Base)

> **Scope note (how to read this document):** This file documents the **chunker** of the NetGuard AI RAG subsystem (`backend/rag/chunking.py`). It explains how the knowledge-base markdown files are split into the small, self-contained pieces that the retriever searches.

---

## Overview

**Chunking** is the step that turns one large markdown document into many smaller, searchable units (chunks) before embedding. It matters because retrieval works at the granularity of chunks: a chunk should be small enough that similarity scoring is meaningful, yet large enough to carry a complete, self-contained thought with enough context to be cited as evidence.

NetGuard AI uses a **markdown-aware chunker** with a default target size of **500 words** and **80 words of overlap** between consecutive windows.

---

## Definition

- **Chunk:** A single searchable unit of text with full provenance metadata (source document, section, category, etc.).
- **Chunk size (500):** Approximate word budget per chunk; sections smaller than this become one chunk.
- **Chunk overlap (80):** Words carried over between consecutive windows of a long section, preserving context across chunk boundaries.
- **Section:** A block of text under a markdown heading (`#` to `###`).
- **Sliding window:** When a section is longer than the chunk size, it is cut into overlapping windows each of the target size.

**Related terms:** text segmentation, windowing, contextual overlap, provenance metadata.

---

## Key Concepts

### Markdown-Aware Splitting
The chunker first splits each document into sections by markdown headings (first-to-third level). Each heading becomes that section's `section_title`, which is carried into chunk metadata. Sections that fit within the chunk size become a single chunk; longer sections are cut with a sliding window.

### Contextual Overlap
For sections that must be split, the window advances by `chunk_size - chunk_overlap` (420 words with the defaults), so each window re-includes 80 words from the previous window. This keeps term boundaries and sentences from being shredded between chunks, which would otherwise hurt the retriever's match quality at seam points.

### Rich Provenance Metadata
Every chunk carries: a stable deterministic chunk id, the raw text, source document name and path, knowledge-base **category**, an **attack type** (or "General"), the markdown **section title**, its index within the document, its token count, and a SHA-256 **content hash** of the text. This metadata is what the retriever exposes as source citations in answers.

### Automatic Category & Attack-Type Inference
The chunker infers the knowledge-base category from the document's directory (`network_security`, `datasets_and_ml`, `soc_procedures`, `mitigation`, else `General Cybersecurity`). It then infers a primary attack type from the filename and content, with benchmark documents checked first so a file such as `cicids2017_guide.md` is not miscategorized as a specific attack merely because it mentions attack families. Attack types include the benchmark labels, probing/reconnaissance, credential attacks, botnet/C2, web attacks, and DoS/DDoS.

---

## Technical Details

### Text Cleaning
Before splitting, the chunker normalizes line endings and collapses runs of more than two blank lines, so chunk boundaries are not distorted by formatting noise.

### Section Handling
- A section at or under the chunk size becomes one chunk titled with its heading (e.g., `## Overview\n\n...`).
- A section above the chunk size becomes multiple chunks, each captioned `## <Section> (Part)`, generated by stepping `start` forward by `chunk_size - chunk_overlap` until the section is exhausted.

### Stable Chunk IDs
Chunk ids are derived from the clean document name, a zero-padded chunk index, and a short MD5 digest of the chunk text, so the same document content re-chunked the same way always yields the same ids - making rebuilds and diffs deterministic.

### Interaction With the Pipeline
Chunking is the first stage of ingestion: chunked output feeds the embedding engine (`rag_embeddings.md`), the vector store (`rag_vector_store.md`), and ultimately the retriever's evidence candidates (`rag_retriever.md`). Tuning chunk size/overlap via `RAG_CHUNK_SIZE` / `RAG_CHUNK_OVERLAP` changes retrieval granularity and memory footprint.

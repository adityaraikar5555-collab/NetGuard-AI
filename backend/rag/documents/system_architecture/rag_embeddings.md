# RAG Embeddings (How Text Becomes Vectors)

> **Scope note (how to read this document):** This file documents the **embedding engine** of the NetGuard AI RAG subsystem (`backend/rag/embeddings.py`). The details match the actual configuration; the default provider is offline TF-IDF so retrieval never depends on an external embedding API.

---

## Overview

**Embeddings** are the numeric vector representations that make similarity search possible. Every knowledge-base chunk and every user query is converted into a fixed-length vector; chunks whose vectors are closest to the query vector (by cosine similarity) are considered (and returned as) the most relevant evidence.

NetGuard AI's default embedding provider is **TF-IDF** from scikit-learn - fully offline, deterministic, and free of external API dependencies. Other providers exist in the code for when they are configured, but TF-IDF is the reliable default used by the current deployment.

---

## Definition

- **Embedding:** A dense numeric vector that captures the vocabulary/content of a piece of text in a way that supports similarity comparison.
- **TF-IDF:** Term Frequency-Inverse Document Frequency - a classic text representation that weights how important a term is to a chunk within the whole corpus.
- **Cosine similarity:** A normalized dot-product between two vectors; values near 1 mean very similar, near 0 mean dissimilar.
- **Vectorizer:** The fitted object that converts raw text into vectors using a learned vocabulary and term weights.

**Related terms:** vectorization, semantic similarity, term weighting, normalized embeddings, vector search.

---

## Key Concepts

### Why Embeddings Are Needed
The retriever cannot compare raw prose. Converting both the query and every chunk into the same vector space lets the vector store rank chunks by geometric similarity, which is fast and captures vocabulary overlap (including hyphenated cybersecurity terms such as `syn-ack`, `slowloris`, `dst_host`).

### TF-IDF Configuration
The TF-IDF vectorizer used at indexing and query time is:
- **n-gram range (1, 2):** unigrams and bigrams, so multi-word signal such as "flow duration" is captured.
- **max_features 1024:** vocabulary is capped at 1024 terms, which fixes the embedding dimension to 1024.
- **sublinear_tf:** log-scaled term frequency so frequently repeated terms don't dominate.
- **token pattern:** a regex that keeps both bare words and hyphenated words (`\b\w[\w-]+\w\b|\b\w+\b`), preserving terms like `dst_host` intact.

The corpus is L2-normalized so that plain dot products equal cosine similarity in the vector store.

### Consistency Between Indexing and Querying
The vectorizer is fitted on the full document corpus during ingestion and persisted to `backend/rag/cache/tfidf_vectorizer.pkl`. Query embeddings are produced by the **same persisted vectorizer**, so a query and the indexed chunks share one vocabulary. Without this, query and chunk vectors could live in different feature spaces and never match.

### Cache Safety
The engine keeps an on-disk embedding cache, but it is deliberately **not reused across providers**: old vectors generated by a different provider/model (e.g., 384-d sentence-transformer vectors vs 1024-d TF-IDF vectors) are not loaded, preventing dimension mismatches that would silently corrupt retrieval.

## Technical Details

### Provider Fallback Chain
`_generate_embeddings()` dispatches in this order:
1. **Sentence-Transformers** (if provider is `sentence_transformers` or `auto` and the package loads).
2. **Gemini API** (if provider is `gemini`, or `auto` with a Gemini key) - `text-embedding-004` batch embeddings, L2-normalized.
3. **OpenAI API** (if provider is `openai`, or `auto` with an OpenAI key) - `text-embedding-3-small`.
4. **TF-IDF + cosine normalization** - the guaranteed built-in fallback (and the configured default).

This means retrieval works even with no network and no API keys: the TF-IDF path always succeeds.

### Embedding Lifecycle During Ingestion
1. `fit_corpus(all_chunk_texts)` fits the TF-IDF vocabulary and saves the vectorizer file.
2. `embed_texts(all_chunk_texts)` computes the L2-normalized 1024-d vectors and stores them in the cache by text hash.
3. The vectors are handed to the vector store for indexing with their chunk metadata.

### Embedding Lifecycle During a Query
`embed_query(query)` calls the same vectorizer on the (expanded) query text and returns a single normalized 1024-d vector. The vector store then computes cosine similarity against every indexed chunk.
